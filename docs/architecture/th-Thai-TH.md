# สถาปัตยกรรมและรายละเอียดการพัฒนา

เอกสารนี้อธิบายว่า Linker ถูกพัฒนาอย่างไร: เป้าหมายการออกแบบและสถาปัตยกรรมภาพรวม โมเดลข้อมูล กลไกหลายภาษา การทำงานร่วมกันแบบเรียลไทม์ และการแบ่งชั้นฝั่งหน้าเว็บพร้อมกลไกสำคัญ อ่านก่อนลงโค้ดหรือต่อยอดพัฒนา จะเห็นภาพรวมได้เร็วขึ้น

เอกสารคู่:

- [เอกสารอ้างอิง API](../api/th-Thai-TH.md): สัญญาภายนอกฉบับเต็ม — เอนด์พอยนต์ REST ข้อความบรอดแคสต์ WebSocket และตารางรหัสข้อผิดพลาดฉบับสมบูรณ์ การสื่อสารระหว่างหน้าเว็บกับแบ็กเอนด์ยึดตามเอกสารนี้
- [README](../../README.th-Thai-TH.md): แนะนำผลิตภัณฑ์ รายการคุณสมบัติ และการเริ่มใช้งาน (ถ้าต้องการแค่ใช้งาน กลับไปที่นี่)

## อภิธานศัพท์

หนึ่งคำจำกัดความต่อบรรทัด เพื่อกำจัดความกำกวม รายละเอียดกลไกยึดตามแต่ละหัวข้อในเนื้อเรื่อง

| คำศัพท์ | คำจำกัดความ |
|---|---|
| องค์กร | โหนดในโครงสร้างแบบต้นไม้ สามารถมีตัวตนและองค์กรลูกได้ (ดู[โมเดลข้อมูล](#โมเดลข้อมูล)) |
| ตัวตน | บทบาทที่นิยามภายในองค์กร (แบบ รัฐมนตรี/สมาชิก) **ไม่ใช่ตำแหน่งงาน** การแปลเป็นภาษาอื่นต้องไม่ใช้คำในหมวดชื่อตำแหน่งงาน |
| บุคคล | เอนทิตีระดับโลกแบบแบน ผูกกับตัวตนผ่าน "การมอบหมาย" |
| การดำรงตัวตน | ความสัมพันธ์แบบหลายต่อหลายระหว่างตัวตนกับบุคคล (แถว `identity_person`) |
| ความสัมพันธ์ | เส้นระหว่างการดำรงตัวตนสองฝั่ง (`person_person`) พร้อมป้ายสองทิศ forward/backward |
| มอบหมาย | การกระทำที่สร้างการดำรงตัวตน "สร้างและมอบหมาย" = สร้างบุคคลและสร้างการดำรงตัวตนในขั้นตอนเดียว |
| ฐานข้อมูล | ไฟล์ `.db` หนึ่งไฟล์ คือฐานข้อมูลอิสระหนึ่งฐานที่บรรจุกราฟฉบับสมบูรณ์ |
| ภาษาอ้างอิงหลัก | การตั้งค่าระดับฐานข้อมูล: ภาษาฐานของชื่อ ช่องอ้างอิงหลักต้องไม่ว่าง และเป็นจุดสิ้นสุดของห่วงโซ่สำรอง (ดู[โมเดลข้อมูลหลายภาษา](#โมเดลข้อมูลหลายภาษา)) |
| ภาษาที่เปิดใช้ | การตั้งค่าระดับฐานข้อมูล (รายการเรียงลำดับ) กำหนดว่าแบบฟอร์มชื่อบันทึกภาษาใดได้บ้างและ JSON ส่งออกมีคอลัมน์ภาษาใดบ้าง |
| ภาษาของหน้าจอ | การตั้งค่าเฉพาะฝั่งหน้าเว็บที่มีผลกับการแสดงผลเท่านั้น จำไว้ต่อฐานข้อมูล ค่าเริ่มต้นคือตามภาษาอ้างอิงหลัก |
| ช่องภาษา | คอลัมน์ของภาษาหนึ่งในตารางแนบ `_l10n` `NULL` = ยังไม่ได้แปล |
| ห่วงโซ่สำรอง | ลำดับการค้นหาชื่อที่แสดง: ช่องภาษาของหน้าจอ → รายการสำรองเฉพาะภาษา (เรียงตามลำดับ เฉพาะภาษาที่เปิดใช้เท่านั้น สามตัวแปรหลัก zh สำรองกันเอง และสองตัวแปร en ก็เช่นกัน) → ช่องภาษาอ้างอิงหลัก |
| การเติมเต็ม | หลังสลับภาษาอ้างอิงหลัก ระเบียนเก่าจะไม่มีค่าในภาษาอ้างอิงหลักใหม่ชั่วคราว การแก้ไขครั้งต่อไปต้องเติมค่ากลับในทันที |
| การอัปเดตแบบออปติมิสติก | การกระทำของหน้าจอลงในแคชภายในและวาดใหม่ก่อน ซิงก์ในพื้นหลัง และย้อนกลับพร้อมดึงข้อมูลใหม่เมื่อล้มเหลว |
| คีย์ชั่วคราว / domKey | สำหรับอ็อบเจ็กต์ที่สร้างในเครื่องแต่ยังไม่ลงฐานข้อมูล: คีย์ Symbol / ตัวระบุ DOM `tmp-N` เมื่อลงฐานข้อมูลแล้ว `adoptId` จะเขียน id จริงกลับ (ดู[การทำงานร่วมกัน](#การทำงานร่วมกัน)) |

## เป้าหมายการออกแบบ

- **Zero dependencies**: ใช้เฉพาะ built-in ของ Node คือ `node:sqlite` + `node:http` โมดูล ES Module ดั้งเดิมของฝั่งหน้าเว็บ ไม่มีขั้นตอนบิลด์ — โคลนแล้วรัน `node server.js` ได้ทันที การดีพลอยไม่มีพื้นผิวภายนอก
- **หลายฐานข้อมูล**: ทุกไฟล์ `.db` ใน `data/` คือฐานข้อมูลอิสระหนึ่งฐาน โหลดตามชื่อเมื่อถูกใช้และแคชการเชื่อมต่อ ฐานข้อมูลแยกขาดจากกันทั้งหมด และการสำรอง/ย้ายข้อมูลคือแค่ไฟล์เดียว
- **ออฟไลน์เป็นหลัก (optimistic update)**: การกระทำของหน้าจอลงในแคชภายในและวาดใหม่ก่อน ในขณะที่คำขอซิงก์ในพื้นหลัง เมื่อล้มเหลวจะย้อนกลับและดึงข้อมูลใหม่โดยอัตโนมัติ ผู้ใช้ไม่ถูกผูกกับจังหวะของเครือข่าย
- **การทำงานร่วมกัน**: หลังเขียน REST สำเร็จ การเปลี่ยนแปลงจะถูกบรอดแคสต์ผ่าน WebSocket ไปยังไคลเอนต์อื่นของฐานข้อมูลเดียวกัน โดยยกเว้นผู้ส่งตาม client id เพื่อป้องกันการวนซ้ำ
- **ข้อมูลหลายภาษาเป็นพลเมืองชั้นหนึ่ง**: ชื่อไม่มีแนวคิด "คอลัมน์ภาษาหลัก" จะถูกจัดเก็บเป็นช่องต่อภาษา และภาษาอ้างอิงหลักเป็นเพียงจุดสิ้นสุดของห่วงโซ่สำรอง

## ภาพรวมสถาปัตยกรรมและวงจรชีวิตของคำขอ

```
Browser ──HTTP──▶ server.js ──┬── static files (public/, home page and database pages)
                              ├── REST /:database/api/* ──▶ db.js (write methods wrapped by wrapDbForCollab)
                              └── WS   /:database/ws      ──▶ ws.js broadcast
```

เส้นทางของการเขียนหนึ่งครั้ง: data.js ฝั่งหน้าเว็บอัปเดตแคชภายในและวาดใหม่ก่อน (แบบออปติมิสติก) จากนั้นส่งคำขอ REST พร้อมหัว `X-Lang` / `X-Client-Id` เมื่อเมธอด db ฝั่งเซิร์ฟเวอร์ที่ถูกห่อด้วย `wrapDbForCollab` สำเร็จ ข้อความเปลี่ยนแปลงจะถูกบรอดแคสต์ตามแผนที่ `OP_BUILDERS` (ยกเว้นผู้ส่ง) เมื่อหน้าเว็บรับบรอดแคสต์ จะสะท้อนการเปลี่ยนแปลงระยะไกลเข้าแคชภายใน เมื่อซิงก์ล้มเหลวจะย้อนกลับ (ดึงข้อมูลทั้งหมดใหม่) ข้อขัดแย้งไม่ถูกรวม — การเขียนพร้อมกันบนทรัพยากรเดียวให้ผลตามครั้งล่าสุด

## โมเดลข้อมูล

คีย์หลักเป็น UUID เสมอและถูกสร้างโดยแบ็กเอนด์ ตารางหลักจัดเก็บเฉพาะโครงสร้างและคีย์อ้างอิง **ชื่อทั้งหมดอยู่ในตารางแนบ `_l10n`** (ช่องอ้างอิงหลักรับประกันว่าไม่ว่าง ดูหัวข้อถัดไป)

### รายการตาราง

| ตาราง | คอลัมน์ | คำอธิบาย |
|---|---|---|
| `organization` | `id` PK · `parent_id` อ้างอิงตัวเอง · `created_at` · `sort_order` | โหนดต้นไม้ขององค์กร |
| `identity` | `id` PK · `organization_id` → องค์กร · `created_at` · `sort_order` | ตัวตนภายในองค์กร |
| `person` | `id` PK · `created_at` | บุคคล แบน ไม่มีต้นไม้ |
| `identity_person` | PK รวม `person_id`+`identity_id` · `created_at` · `sort_order` | การดำรงตัวตน (หลายต่อหลาย) การเรียงลำดับใช้เฉพาะภายในตัวตน |
| `person_person` | `id` PK · `a_person_id`/`a_identity_id`/`b_person_id`/`b_identity_id` · `created_at` | ความสัมพันธ์ แต่ละปลายคือ "การดำรงตัวตน" |
| `meta` | `id` PK · `value` | เมทาดาทาแบบคีย์-ค่า (`authoritative_lang` / `enabled_langs` / `bg_color` ฯลฯ) |
| `organization_l10n` / `identity_l10n` / `person_l10n` | `id` PK → ตารางหลัก · หนึ่งคอลัมน์ต่อภาษา | ช่องชื่อ หนึ่งแถวต่อหนึ่งเอนทิตี |
| `person_person_l10n` | PK รวม `id`+`type`(forward/backward) · หนึ่งคอลัมน์ต่อภาษา | ช่องป้ายสองทิศของความสัมพันธ์ |
| `meta_l10n` | `id` (= คีย์เมทาดาทา) · หนึ่งคอลัมน์ต่อภาษา | ช่องสำหรับชื่อที่แสดง (display_name) |

คอลัมน์ภาษาตั้งชื่อด้วยรหัสอย่าง `zh_Hans_CN` (แทน `-` ด้วย `_`) `NULL` = ยังไม่ได้แปลเป็นภาษานั้น

### การย้ายข้อมูลและการเรียงลำดับ

- **ช่องเรียงลำดับ**: `sort_order` ถูกเพิ่มให้องค์กร / ตัวตน / identity_person โดยการย้ายข้อมูล `ensureSortColumn` (ฐานข้อมูลเก่าถูกเติมค่าย้อนหลังตาม rowid) ลำดับพี่น้องทั้งหมดถูกเขียนใหม่โดย `reorderSiblings` (แก้หนึ่งแถว เขียนทั้งคอลัมน์ใหม่ เพื่อแลกกับการอ่านที่ไม่ต้องเรียงลำดับ)
- **วิวัฒนาการคอลัมน์ภาษา**: `ensureL10nColumns` เพิ่มคอลัมน์ภาษาที่เพิ่งถูกเพิ่มใน `LANGS` ให้กับตารางแนบ l10n ทั้งห้า — การเพิ่มภาษาไม่ได้ปรับเลขเวอร์ชันสคีมา เป็นการพัฒนาตามปกติ

### กฎการลบตามลูกโซ่

- การลบบุคคล: ล้างการดำรงตัวตนทั้งหมดของบุคคลนั้นและความสัมพันธ์ที่บุคคลนั้นเป็นปลาย
- การลบองค์กร: ลบทั้งต้นไม้ย่อยแบบเวียนใหม่โดยค่าเริ่มต้น ด้วย `promote=1` จะเก็บองค์กรลูกไว้และเลื่อนขึ้นไปแทนที่องค์กรที่ถูกลบ
- การลบตัวตน: ล้างการดำรงตัวตน และปลายทางความสัมพันธ์ถูกชี้เป้าใหม่ตามไป (บรอดแคสต์ `personPerson:retarget` นำข้อมูลทั้งหมดไปด้วย)

## โมเดลข้อมูลหลายภาษา

แนวคิดภาษาสามตัว แต่ละตัวมีหน้าที่ของตัวเอง:

| แนวคิด | จัดเก็บที่ | หน้าที่ |
|---|---|---|
| ภาษาอ้างอิงหลัก | `meta.authoritative_lang` (หนึ่งต่อฐานข้อมูล) | ภาษาฐานของชื่อ ช่องอ้างอิงหลักต้องไม่ว่าง และเป็นจุดสิ้นสุดของห่วงโซ่สำรองการแสดงผล |
| ภาษาที่เปิดใช้ | `meta.enabled_langs` (สตริงคั่นด้วยจุลภาค เรียงลำดับ) | กำหนดว่าแบบฟอร์มชื่อบันทึกภาษาใดได้บ้างและ JSON ส่งออกมีคอลัมน์ใดบ้าง ต้องมีภาษาอ้างอิงหลักและอยู่ลำดับแรกเสมอ |
| ภาษาของหน้าจอ | localStorage ฝั่งหน้าเว็บ (`linker:locale` ทั้งหมด + `linker:view:<path>` เขียนทับต่อฐานข้อมูล) | มีผลกับการแสดงผลเท่านั้น ไม่เข้าฐานข้อมูล |

**ห่วงโซ่สำรองการแสดงผล**: ช่องภาษาของหน้าจอ → รายการสำรองเฉพาะภาษา (เรียงตามลำดับ ลองเฉพาะช่องของภาษาที่เปิดใช้เท่านั้น — เช่น zh-Hant-HK→zh-Hant-TW→zh-Hans-CN สำรองกันเอง รวมถึง en-Latn-GB กับ en-Latn-US) → ช่องภาษาอ้างอิงหลัก → (การสำรองด้วยสตริงว่างถูกจัดการโดยผู้เรียก) แคชฝั่งหน้าเว็บถือครองทุกช่อง การสลับภาษาของหน้าจอจึงเป็นการแก้ค่าใหม่ในหน่วยความจำล้วน (`reresolveAll`) ไม่ต้องติดต่อแบ็กเอนด์ การสลับชุดภาษาที่เปิดใช้ก็กระตุ้นการแก้ค่าใหม่ทั้งหมดเช่นกัน (โหนดที่ใช้ได้ของห่วงโซ่สำรองเปลี่ยนตามไปด้วย)

**สัญญาการเขียน**: เอนด์พอยนต์เขียนรับชุด superset `{authoritative, value, l10n}` พร้อมหัว `X-Lang` อย่างสม่ำเสมอ —

- สร้าง (`createPayload`): `authoritative` ค่าเริ่มต้นย้อนกลับไปที่ `value` ช่องอ้างอิงหลักต้องไม่ว่างในที่สุด มิฉะนั้น `authoritative_required`
- อัปเดต (`namePatch`): `l10n` อัปเซิร์ตทีละช่อง **สตริงว่างลบช่อง** (ยกเว้นช่องอ้างอิงหลักที่ห้ามลบ)
- เมื่อสร้างฐานข้อมูล ภาษาอ้างอิงหลักถูกปลูกจาก `X-Lang` ของผู้สร้าง ฐานข้อมูลที่มีอยู่ถูกตั้งเป็น zh-Hans-CN ทั้งหมดตอนย้ายข้อมูล (ครั้งเดียว เสร็จแล้ว)

**กฎการเติมเต็ม**: หลังสลับภาษาอ้างอิงหลัก ระเบียนเก่าจะไม่มีชื่อในภาษาอ้างอิงหลักใหม่ชั่วคราว (การแสดงผลกลับไปใช้ค่าอ้างอิงหลักเดิม) การแก้ไขระเบียนนั้นครั้งต่อไปต้องเติมค่าอ้างอิงหลักกลับในทันทีก่อนจึงจะบันทึกได้

รูปแบบการแสดงของแบบฟอร์ม (ช่องป้อนเดี่ยว / อ้างอิงหลัก + ปัจจุบัน + ห่วงโซ่สำรอง / ทุกภาษาที่เปิดใช้) ถูกตัดสินโดยสวิตช์ "การป้อนข้อความ" แบบสามตัวเลือกกันทับกันของฝั่งหน้าเว็บ และไม่มีผลต่อเอนด์พอยนต์การเขียน — สัญญาอินเทอร์เฟซอยู่ใน [เอกสาร api](../api/th-Thai-TH.md)

## การทำงานร่วมกัน

- **การอัปเดตแบบออปติมิสติก**: ทุก op ใน `data.js` อัปเดตแคชภายในและเรียก `notify` เพื่อวาดใหม่ก่อน จากนั้นยิง `api()` ในพื้นหลัง เมื่อล้มเหลว `loadAll()` จะดึงข้อมูลทั้งหมดใหม่เพื่อย้อนกลับ
- **คีย์ชั่วคราว (tempKey)**: อ็อบเจ็กต์ที่สร้างในเครื่องแต่ยังไม่ลงฐานข้อมูลใช้ Symbol เป็นคีย์ และลงทะเบียน `domKey` ด้วย (สตริง `tmp-N` ใช้กับแอตทริบิวต์ DOM และการแฮชสี) เมื่อเซิร์ฟเวอร์ส่ง id จริงกลับมา `adoptId` เขียนกลับและซิงก์ id/l10n ของรายการการดำรงตัวตนในต้นไม้ (มิฉะนั้นการเลือกสีชิปและการแก้ค่าภาษาจะค้างอยู่ที่ค่าตัวยึดตำแหน่ง)
- **บรอดแคสต์**: `ws.js` คือสับเซ็ตของ RFC 6455 (บรอดแคสต์ข้อความ + ping/pong + ฮาร์ตบีต) เมธอดเขียน → ข้อความถูกแมปโดย `OP_BUILDERS` และการเขียนหนึ่งครั้งอาจให้หลายข้อความ (เช่น การเลื่อนการดำรงตัวตน = assign + unassign + retarget หลายตัว) op และฟิลด์ทั้งหมดอยู่ใน [เอกสาร api](../api/th-Thai-TH.md)
- **นโยบายข้อขัดแย้ง**: ไม่รวม — ให้ผลตามครั้งล่าสุด เมื่อการลบของผู้อื่นโดนอ็อบเจ็กต์ที่คุณกำลังแก้ไข คุณจะถูกบังคับออกจากโหมดแก้ไข (ล้างสแต็กโมดัล)

## สถาปัตยกรรมฝั่งหน้าเว็บ

การไหลของข้อมูลแบบชั้น: `events.js` (การแทนที่เหตุการณ์แบบรวม) → `controls.js` / `data.js` (การกระทำและข้อมูล) → `html.js` (ฟังก์ชันบริสุทธิ์ที่ผลิตข้อความ HTML/SVG) → `view.js` (การติดตั้ง DOM) ชั้นเรนเดอร์ไร้สถานะ สถานะมีสามชนิด:

| สถานะ | ตำแหน่ง | คำอธิบาย |
|---|---|---|
| แคชข้อมูล `store` | `data.js` | ต้นไม้องค์กร บุคคล ความสัมพันธ์ เมทาดาทา — สะท้อนเซิร์ฟเวอร์ฉบับเต็ม |
| สถานะมุมมอง `vs` | `view.js` | ซูม/โฟกัส/พับ จัดเก็บต่อฐานข้อมูลลง `linker:view:<path>` |
| การตั้งค่า | `settings.js` / localStorage | การตั้งค่าเฉพาะเครื่อง เช่น สวิตช์การป้อนข้อความ |

คำศัพท์หน้าจอถูกค้นผ่าน `i18n.js` (ไม่มีคำศัพท์จะแสดงคีย์เอง) ข้อความสถิตถูกมาร์กด้วย `data-i18n` และสลับอย่างเป็นระบบโดย `applyStatic()` สคริปต์อินไลน์ใน `head` ซ่อนหน้าจนคำศัพท์พร้อม เพื่อกันพริบ

## รายละเอียดแบบฟอร์มและการส่งออก

- **รูปแบบแบบฟอร์มชื่อ**: รูปแบบถูกตัดสินโดยสวิตช์ "การป้อนข้อความ" แบบสามตัวเลือกกันทับกัน — bare (ช่องป้อนเดี่ยว) / dual (อ้างอิงหลัก + ปัจจุบัน + ภาษาในห่วงโซ่สำรอง ตัวเลือก 2 "แสดงภาษาอ้างอิงหลักและห่วงโซ่สำรอง") / full (ทุกภาษาที่เปิดใช้) แถวอ้างอิงหลักอยู่แรกเสมอ ตัวหนา บังคับกรอก และลบให้ว่างไม่ได้ การแก้ไขและการสร้างที่ช่องอ้างอิงหลักว่าง บังคับแสดงแถวอ้างอิงหลักตามกฎของ fill (ดูหมายเหตุใต้ตาราง) bare/fill ต้องการให้ภาษาของหน้าจออยู่ในชุดภาษาที่เปิดใช้ หากไม่อยู่ จะรวมเป็น "ช่องป้อนเดี่ยวอ้างอิงหลักที่มีป้าย" dual เป็นข้อยกเว้น — ภาษาของหน้าจอไม่อยู่ในชุดภาษาที่เปิดใช้แต่มีภาษาในห่วงโซ่สำรองที่เปิดใช้ ยังคงใช้ได้ (ชุดแถว = อ้างอิงหลัก + ภาษาในห่วงโซ่ การแก้ไขหลายภาษานอกมาตรฐาน ดูตาราง)

| ภาษาของหน้าจอ | ภาษาที่เปิดใช้ | ภาษาอ้างอิงหลัก | ช่องอ้างอิงหลักว่าง | ตัวเลือก 1 | ตัวเลือก 2 | ตัวเลือก 3 | สถานการณ์ |
|---|---|---|---|---|---|---|---|
| A | รวม A | A | ใช่ | A ไม่มีป้าย | A (+ภาษาในห่วงโซ่สำรองของ A) มีเฉพาะ A จึงไม่มีป้าย | ทั้งหมด มีป้าย | สร้างปกติ |
| A | รวม A | A | ไม่ใช่ | A ไม่มีป้าย | A (+ภาษาในห่วงโซ่สำรองของ A) มีเฉพาะ A จึงไม่มีป้าย | ทั้งหมด มีป้าย | แก้ไขปกติ |
| A | รวม A | B | ใช่ | B และ A มีป้าย | อ้างอิงหลัก A และภาษาในห่วงโซ่สำรองของ A มีป้าย | ทั้งหมด มีป้าย | สร้างหลายภาษาหรือแก้ไขในช่วงเติมเต็ม |
| A | รวม A | B | ไม่ใช่ | A ไม่มีป้าย | อ้างอิงหลัก A และภาษาในห่วงโซ่สำรองของ A มีป้าย | ทั้งหมด มีป้าย | แก้ไขหลายภาษา |
| A | ไม่รวม A | B | ใช่ | B มีป้าย | อ้างอิงหลัก (+ภาษาในห่วงโซ่สำรองของ A) มีป้าย | ทั้งหมด มีป้าย | สร้างนอกมาตรฐาน |
| A | ไม่รวม A | B | ไม่ใช่ | B มีป้าย | อ้างอิงหลัก (+ภาษาในห่วงโซ่สำรองของ A) มีป้าย | ทั้งหมด มีป้าย | แก้ไขนอกมาตรฐาน |

ภาษาในห่วงโซ่สำรอง = รายการสำรองเฉพาะภาษา ∩ ชุดภาษาที่เปิดใช้ (`LANG_FALLBACK` ดู[โมเดลข้อมูลหลายภาษา](#โมเดลข้อมูลหลายภาษา)) ลำดับแถว: อ้างอิงหลักอยู่แรกเสมอ ตามด้วยภาษาปัจจุบัน แล้วเรียงตามลำดับห่วงโซ่ การส่งของ dual ใช้กฎเดียวกับ full (รวบรวมเฉพาะแถวที่เรนเดอร์แล้ว สตริงว่างลบช่อง)
รูปแบบเติมเต็ม fill: บังคับใช้เมื่อช่องอ้างอิงหลักว่าง + อ้างอิงหลัก ≠ ภาษาของหน้าจอ + ไม่ได้เลือกตัวเลือก 2 (การสร้างใหม่กระตุ้นเสมอ) — มีเฉพาะสองแถว อ้างอิงหลัก + ปัจจุบัน ไม่มีภาษาในห่วงโซ่ เมื่ออ้างอิงหลัก = ภาษาของหน้าจอ ช่องป้อนเดี่ยว bare ก็เติมค่าช่องอ้างอิงหลักกลับได้ (ฝั่งเซิร์ฟเวอร์ `value` ค่าเริ่มต้นย้อนกลับไปที่ `authoritative`) ไม่บังคับหลายแถว

การพัฒนา: ดู settings.js nameModalMode
- **ป็อปอัพชื่อเรื่อง** (ชื่อที่แสดงของฐานข้อมูล): ไม่มีแนวคิดอ้างอิงหลักและไม่มีแถวตัวหนา แก้ไขได้เฉพาะภาษาที่เปิดใช้เท่านั้น (ภาษาที่ไม่ได้เปิดใช้ไม่ปรากฏในช่องแก้ไข) การแสดงชื่อเรื่องสำรองตามห่วงโซ่เดียวกับชื่อ (ช่องของหน้าจอ → รายการสำรองเฉพาะภาษา ∩ ชุดภาษาที่เปิดใช้) หากห่วงโซ่หมดแล้วยังว่าง จะสำรองเป็นชื่อฐานข้อมูล การส่งไม่เขียน authoritative รูปแบบอยู่ในตารางด้านล่าง ("ทั้งหมด" = ทุกภาษาที่เปิดใช้):

| ภาษาของหน้าจอ | ภาษาที่เปิดใช้ | ตัวเลือก 1 | ตัวเลือก 2 | ตัวเลือก 3 |
|---|---|---|---|---|
| A | รวม A | A ไม่มีป้าย | A + ภาษาในห่วงโซ่สำรองของทุกภาษาที่เปิดใช้ มีหลายภาษาจึงมีป้าย มีเฉพาะ A จึงไม่มีป้าย | ทั้งหมด มีป้าย |
| A | ไม่รวม A | ชื่อฐานข้อมูลแบบอ่านอย่างเดียว (แก้ไขไม่ได้) | ภาษาในห่วงโซ่สำรองของทุกภาษาที่เปิดใช้ มีป้าย ถ้าไม่มีเลย จะแสดงชื่อฐานข้อมูลแบบอ่านอย่างเดียว | ทั้งหมด มีป้าย |

  ลำดับแถว: ตัวเลือก 3 ภาษาปัจจุบัน (เมื่อ ∈ ชุดที่เปิดใช้) อยู่แรกเสมอ ที่เหลือเรียงตามลำดับภาษาที่เปิดใช้ (อ้างอิงหลักอยู่แรกเสมอ) เมื่อภาษาของหน้าจอ ∉ ชุดที่เปิดใช้ ทั้งหมดเรียงตามลำดับภาษาที่เปิดใช้ ตัวเลือก 2 เรียงตามลำดับห่วงโซ่สำรอง (A อยู่แรก) placeholder = การแสดงชื่อเรื่องโดยสมมติว่าช่องนี้ว่าง (ห่วงโซ่หมดแล้วจะสำรองเป็นชื่อฐานข้อมูล)
- **กฎแถวเดียว** (ใช้ร่วมกันในแบบฟอร์มชื่อ / ชื่อเรื่อง / ความสัมพันธ์): เมื่อผลการเรนเดอร์ของรูปแบบหลายภาษาเหลือเพียงหนึ่งแถว/หนึ่งกลุ่ม และเป็นเพียงภาษาของหน้าจอปัจจุบัน (อ้างอิงหลัก = หน้าจอ และเป็นฐานข้อมูลภาษาเดียวที่เปิดใช้เฉพาะอ้างอิงหลัก) จะตัดป้ายออก — รูปลักษณ์เหมือนช่องป้อนเดี่ยว แต่สัญญาการส่งยังคงเป็นรูปแบบเดิม
- **การตอบกลับการตรวจสอบการป้อน**: ช่องบังคับเว้นว่าง → กรอบแดงที่ช่องป้อนที่เกี่ยวข้อง + โฟกัสอัตโนมัติ พร้อมการแจ้งเบาที่ลอยขึ้นด้านล่างและหายไปเอง ไม่ปฏิเสธเงียบ ๆ
- **ชื่อไฟล์ส่งออก** (PNG/SVG): `brand_display-name_timestamp.ext` โดยชื่อแบรนด์ตามภาษาของหน้าจอ การส่งออกมุมมอง "ปัจจุบัน" เติมชื่อองค์กร
- **มือถือ**: ช่องป้อน ≥16px เพื่อป้องกันการซูมตอนโฟกัสบน iOS

## ข้อตกลงข้อผิดพลาด

แบ็กเอนด์ส่งกลับเฉพาะรหัสข้อผิดพลาด (`{error: code}` เช่น `org_not_found`) ข้อความข้อผิดพลาดถูกดูแลในคำศัพท์ l10n ฝั่งหน้าเว็บ (`error.*`) ตามภาษาของหน้าจอ รหัสข้อผิดพลาดของการตรวจสอบ เช่น "ช่องอ้างอิงหลักบังคับ" และ "ห้ามลบ" คือ `authoritative_required` และ `authoritative_lang_invalid` ตารางรหัสข้อผิดพลาดฉบับเต็มอยู่ใน [api/th-Thai-TH.md](../api/th-Thai-TH.md)

  data.js        ชั้นข้อมูล: การสื่อสารแบ็กเอนด์ การอัปเดตแบบออปติมิสติก กลไกคีย์ชั่วคราว การแก้ค่าหลายภาษาและแก้ใหม่ การสะท้อนการเปลี่ยนแปลงระยะไกล
  export.js      การส่งออก: การประกอบภาพ PNG/SVG ดาวน์โหลด JSON/DB ชื่อไฟล์
  settings.js    โหมดการป้อนข้อความ (สามตัวเลือก แต่ละตัวกันทับกัน บังคับเลือก) และการตัดสินรูปป็อปอัปชื่อ/ความสัมพันธ์ สวิตช์จัดเก็บใน localStorage (กำหนดรูปแบบบอดี้คำขอ)
  i18n.js        กรอบ i18n: การลงทะเบียน l10n การค้นหา t() พร้อมแทรกค่า การจัดเก็บ localStorage การแจ้งเปลี่ยนแปลง applyStatic
  l10n/          คำศัพท์ภาษาหน้าจอ (ไม่มีคำศัพท์จะแสดงคีย์เอง ทั้งสิบภาษาใช้ชุดคีย์เดียวกัน)
